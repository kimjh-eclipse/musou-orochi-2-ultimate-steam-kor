# 패처·재구성·백업

`patcher/WO3USteamPatch.cs`(C# 5, .NET Framework 4.x, WinForms)는 PS3판 빠른 패처와 같은 화면 흐름을 씁니다. 설치 경로 → 백업 경로 → 주의사항 동의 → 상태 검사·패치·복구 순서이며, 같은 기능을 명령줄로도 쓸 수 있습니다.

## 재구성 방식을 쓴 이유

한국어 `LINKFILE_CHS.BIN`은 교체 항목의 크기가 바뀌어 뒤 항목 오프셋이 모두 달라집니다([아카이브 구조](formats.md)). 원본과 완성본을 바이트 단위로 비교하면 파일 대부분이 달라지므로, PS3판처럼 바뀐 구간만 덮어쓰는 방식은 쓸 수 없습니다.

대신 패처가 **완성본 인덱스 순서대로 파일을 새로 씁니다.**

```text
for id in 완성본 IDX의 사용 항목 (완성본 오프셋 순):
    0으로 완성본 오프셋까지 채움
    if id 가 팩에 있음: 팩의 저장 바이트
    else:               사용자 원본 LINKFILE 의 같은 id 저장 바이트
0으로 완성본 파일 크기까지 채움
```

바뀌지 않은 항목은 사용자의 게임 파일에서 복사하므로, 배포 팩에는 한국어로 바뀐 항목(v20261010 기준 1,164개)과 `dinput8.dll`만 들어갑니다.

## 팩 형식: WO3USTM1

정수는 리틀 엔디언입니다.

```text
8 bytes  magic = "WO3USTM1"
i32      format_version = 2 (v20260927은 1)
u16 + B  release (UTF-8)
2 x      파일 레코드 (LINKIDX_CHS.BIN, LINKFILE_CHS.BIN):
  u16 + B  이름
  u64      원본 크기     32 B 원본 SHA-256
  u64      완성본 크기   32 B 완성본 SHA-256
u32 + B  완성본 LINKIDX_CHS.BIN 전체
u32      추가 파일 수 (형식 2만, 현재 1)
각 추가 파일: u16 + B 이름, 32 B SHA-256, u32 + B 바이트   (dinput8.dll)
u32      항목 수
각 항목 (id 오름차순):
  u32 id   u64 길이   저장 바이트(압축 상태 그대로)
```

리더는 파일 순서·인덱스 크기·항목 순서·범위·팩 끝의 남는 데이터를 검사합니다.

## 상태 판별

두 파일의 크기로 원본/완성본 후보를 먼저 가리고, SHA-256으로 확정합니다.

| 상태 | 조건 | 동작 |
|---|---|---|
| 원본 | 두 파일 모두 원본 해시 | 패치 가능 |
| 완성본 | 두 파일 모두 이 버전의 완성본 해시 | 다시 쓰지 않음 |
| 이전 버전 | 지정한 백업이 기록한 완성본 해시와 일치 | 백업으로 원본 재구성 후 새 버전 적용 |
| 알 수 없음 | 그 밖 | 중단, Steam 무결성 검사 안내 |

## 백업 형식: WO3USBK1

백업에는 **원본에서 교체되는 항목의 원본 저장 바이트**와 원본 인덱스만 저장합니다(이번 버전 약 300MB). 원본 파일 전체를 복사하지 않습니다.

```text
8 bytes  magic = "WO3USBK1"
i32      format_version = 1
u16 + B  백업을 만든 패치 버전
2 x      파일 레코드 (팩과 같은 구조: 원본·완성본 크기와 해시)
u32 + B  원본 LINKIDX_CHS.BIN 전체
u32      항목 수, 각 항목: u32 id, u64 길이, 원본 저장 바이트
```

복구는 같은 재구성을 반대 방향으로 합니다. 현재(완성본) 파일과 원본 인덱스를 기준으로, 백업에 있는 항목은 백업에서, 나머지는 현재 파일에서 가져와 원본을 만듭니다. 백업이 기록한 완성본 해시와 현재 파일이 같을 때만 복구합니다.

## 쓰기 순서

1. 게임 실행 여부(`WO3U.exe`), 여유 공간, 쓰기 권한을 확인합니다. Program Files처럼 권한이 없으면 관리자 권한으로 다시 실행할지 묻습니다.
2. 백업을 `.tmp`로 쓰고 구조를 다시 읽어 확인한 뒤 이름을 바꿉니다.
3. 새 `LINKFILE_CHS.BIN`을 `.wo3u-new`로 쓰면서 SHA-256을 계산합니다. 완성본 해시와 다르면 임시 파일을 지우고 중단합니다.
4. 새 인덱스도 `.wo3u-new`로 씁니다.
5. 두 파일을 교체합니다. 기존 파일은 `.wo3u-old`로 옮겼다가 교체가 끝나면 지웁니다. 도중에 실패하면 `.wo3u-old`로 되돌립니다.
6. 교체 후 두 파일 해시를 다시 확인합니다. 어긋나면 백업으로 원본을 재구성합니다.

## dinput8.dll 프록시

`WO3U.exe` 안의 중국어 문장 27개는 실행 파일을 고칠 수 없어(Steam 오류 51) 메모리에서 바꿉니다. 게임이 기본으로 불러오는 `dinput8.dll`을 설치 폴더에 두면 이쪽이 먼저 로드됩니다(`patcher/dll/wo3u_kr_dinput8.c`).

- `DllMain`은 자기 핸들만 저장합니다. 원래 DLL 로드와 모든 작업은 게임이 처음 `DirectInput8Create`를 부를 때 합니다.
- 설치된 `LINKIDX_CHS.BIN`의 크기·CRC32가 표를 만든 빌드와 같은지 먼저 확인합니다. 한국어 바이트는 그 빌드의 폰트 배정에서만 맞기 때문입니다.
- 27개 자리 모두 원래 중국어 바이트와 일치할 때만 씁니다. 하나라도 다르면(게임 업데이트 등) 아무것도 쓰지 않습니다.
- 주소는 파일 오프셋이 아니라 RVA(예: 파일 `0xAC6068` → RVA `0xAC7868`)이며, 실행 중 EXE 모듈 기준 주소에 더합니다.
- 결과는 설치 폴더의 `WO3U_KR_dll.log`에 한 번 기록합니다.
- 나머지 DirectInput 함수는 `System32\dinput8.dll`로 그대로 넘깁니다.

Windows SDK와 C 런타임 없이 MSVC `cl`·`lib`·`link`만으로 빌드합니다(`patcher/dll/build_dll.cmd`). 교체 표는 `tools/gen_dll_patch.py <빌드>`가 만들며, 슬롯 크기·색상 코드·서식 토큰·메시지 코드를 검사합니다.

팩 형식 2는 완성본 인덱스와 항목 목록 사이에 추가 파일 목록을 두고 `dinput8.dll`을 담습니다(위 팩 형식 참고). `build_steam_pack.py`는 DLL 표의 CRC가 빌드 인덱스와 다르면 팩을 만들지 않습니다.

패처는 적용 뒤 DLL을 설치하고 해시를 확인하며, 원본 복구 때 지웁니다. 설치 폴더에 표식이 없는 다른 `dinput8.dll`이 있으면 사용자에게 묻습니다(GUI는 네 버튼, 콘솔은 C/O/S/N, Enter = C).

| 선택 | 동작 |
|---|---|
| 이어서 쓰기(기본) | 기존 파일을 `dinput8_wo3u_chain.dll`로 옮기고 설치. 한국어 DLL이 이 파일을 불러와 모든 호출을 넘김. 원본 복구 때 되돌림 |
| 덮어쓰기 | 기존 파일을 `dinput8.dll.wo3u-orig`로 옮기고 설치. 보관 파일이 이미 있으면 그것은 시각을 붙인 이름으로 남김. 원본 복구 때 되돌림 |
| 건너뛰기 | 데이터만 적용하고 경고. 원본 복구 때도 그 파일은 건드리지 않음 |
| 중단 | 아무것도 바꾸지 않음 |

명령줄 `--yes`는 묻지 않고 이어서 씁니다. `--chain-dll` / `--overwrite-dll` / `--skip-dll`로 정할 수 있습니다. 시나리오 시험은 `patcher/test_scenarios_c.sh`, `test_scenarios_d.sh`.

DLL 쪽 이어서 불러오기: 첫 호출 때 같은 폴더의 `dinput8_wo3u_chain.dll`을 불러오고, 있으면 모든 내보내기 호출을 그 DLL로 넘깁니다(없으면 `System32\dinput8.dll`). 이어서 불린 DLL이 이름만으로 `dinput8.dll`을 불러 한국어 DLL로 되돌아오는 경우에는 재진입 깊이로 감지해 시스템 DLL로 보냅니다. 로그에 `chained: dinput8_wo3u_chain.dll loaded`가 남습니다. 시험: `patcher/dll/chain_test/fake_mod.c`(이름으로 되돌아오는 최악의 경우를 흉내 내는 가짜 모드).

## 선택: 병사 공격성 강화

GUI의 체크박스(기본 해제, 이미 적용된 폴더면 문구에 '[현재 적용됨]' 표시) 또는 명령줄 `--soldier-ai` / `--no-soldier-ai`. 체크한 채 [한국어 패치 적용] = 적용, 해제한 채 적용 = 원래대로, [원본 복구] = 원래대로. 명령줄에서 둘 다 생략하면 지금 상태를 유지합니다.

- 대상: 공통 데이터 `LINKFILE_000.BIN` 0x44CDA의 유닛 표(2,206 슬롯 × 40바이트). 슬롯의 +0은 이름 번호, +32(u16)는 AI 단계(병사 0 / 일반 무장 3 / 조작 무장 5 / 여포 7), +34는 유닛 분류(병사 0, 무장 1, 병기 15~19, 거점·수비병장 20, 백성 22 등), +35는 행동 유형입니다.
- 바꾸는 것(v20261007): 이름으로 고른 근접 병사 263 슬롯의 AI 단계를 1(일반)·3(오로치 병사, 십장·부장·거점병장·수비병장)으로 올리고 분류 1·행동 4(무장 AI)로 바꿉니다. 기마병(행동 2, 무장 AI로 바꾸면 멈춤)·방패병(행동 96)·원거리 병사(분류 2·7 또는 행동 1·20·80·88, AI 단계만 올려도 공격이 과함)는 그대로 둡니다. v20261002b가 쓴 표(364 슬롯)도 알아보고 먼저 원본으로 되돌린 뒤 지금 선택을 적용합니다. 병기·백성·진지 가게·동물·전령·수송·보조형 닌자·술사·장수는 바꾸지 않습니다.
- AI 단계만 올리면 병사가 빨리 다가오기만 하고 공격은 늘지 않았고, 분류·행동을 무장 값으로 바꾸자 공격이 늘었습니다(게임 화면 확인). 무장 AI 아래에서는 AI 단계가 높을수록 근접이 지나치게 적극적이어서 1/3으로 정했습니다.
- 바뀌는 779바이트의 위치·원래 값·새 값과 표 전체의 원본/적용 SHA-256이 패처에 들어 있습니다. 원래 값이 패처 안에 있으므로 따로 백업하지 않고, 표 해시로 원본/적용/기타를 판별합니다. 기타(다른 유닛 모드)는 건드리지 않습니다.
- 표 생성: `tools/soldier_ai3.py table` → `patcher/soldier_ai_table.txt` → `patcher/_edit_soldier_option.py`(소스의 `// <soldier-ai-table>` 블록 갱신). 대상 선택에 쓰는 이름 대응표(`mapping/pc_match.jsonl`)는 게임 원문을 담고 있어 저장소에 포함하지 않습니다. 시험: `patcher/test_scenarios_e.sh`.
- 참고: 유닛 표 위치와 필드 구성은 PythWare의 [Kybernes-Tools](https://github.com/PythWare/Kybernes-Tools) WO3 Unit Editor, 분류·행동 값을 함께 바꾸는 방식은 같은 제작자의 넥서스 모드 Super Aggressive AI, 병사 AI 값 조사는 디시인사이드 진삼국무쌍8 갤러리 SPlT 님의 글을 참고했습니다. 이 도구들의 파일은 포함하지 않습니다.

## 선택: 장수 공격성 한 단계 올리기

GUI의 두 번째 체크박스(기본 해제) 또는 `--officer-ai` / `--no-officer-ai`. 같은 유닛 표에서 분류 1(무장)이고 AI 단계가 3 또는 5인 이름 있는 장수 1,560 슬롯의 AI 단계를 한 단계 올립니다(3→4, 5→6, 여포 7과 2P 슬롯은 그대로). 병사 옵션과 바이트가 겹치지 않아 따로 켜고 끕니다. 표: `tools/soldier_ai3.py officer-table` → `patcher/officer_ai_table.txt` → `patcher/_edit_officer_option.py`.

두 옵션이 같은 표를 쓰므로 표 전체 해시 하나로는 상태를 알 수 없습니다. 옵션마다 바뀌는 바이트가 모두 원래 값/새 값인지로 적용 여부를 보고, 적용된 옵션(이전 판 병사 표 포함)을 모두 걷어낸 표가 원본 해시와 같을 때만 우리 변경으로 봅니다. 그렇지 않으면(다른 유닛 모드) 두 옵션 모두 건드리지 않습니다. 시험: `patcher/test_scenarios_g.sh`.

## 공통 데이터: DLC 의상 출전 문구

갤러리의 '의상 출전'은 DLC 의상마다 공통 데이터 `LINKFILE_003.BIN`에 있는 작은 압축 항목(423개)에서 읽습니다. 항목마다 일본어·영어·번체·간체 4개 언어 레코드가 있고, 게임 언어가 간체면 간체 레코드를 보여 주므로 중국어 원문이 한국어 글꼴로 깨져 보였습니다.

- `tools/gen_common003.py`가 간체 레코드 자리(원래 문자열 + 뒤 여백)에 한국어를 넣고 다시 압축해, 원래 저장 크기 안에 들어가는 것만 팩의 `LINKFILE_003.patch`로 냅니다(16가지 문구, 423개 모두 들어감). 비압축 크기와 인덱스는 바뀌지 않습니다.
- 패처는 한국어 패치를 적용할 때 블록마다 SHA-256이 원본이면 원래 블록을 `WO3U_KR_003.wo3u-backup`에 저장한 뒤 한국어 블록을 쓰고, [원본 복구] 때 되돌립니다. 원본도 한국어도 아닌 블록(게임 업데이트, 다른 모드)은 건드리지 않습니다. 이전 패처는 이 팩 항목을 무시합니다.
- 시험: `patcher/test_scenarios_f.sh`(희소 파일 사본).

## 명령줄

```text
WO3U_Steam_KR_Patch.exe [--folder <설치 폴더>] [--backup <백업 파일>]
                        [--verify-only | --restore] [--yes] [--chain-dll | --overwrite-dll | --skip-dll]
                        [--soldier-ai | --no-soldier-ai] [--no-pause]
```

`--folder`를 생략하면 Steam 설치 폴더를 자동으로 찾습니다. 종료 코드는 성공 0, 실패 1, 상태 검사에서 알 수 없는 상태 2입니다.

## 빌드

```powershell
py -3.13 patcher/build_steam_pack.py <버전> build/<빌드>     # 팩 + 재구성 자가검증
py -3.13 patcher/build_package.py <버전>                     # csc → 패키지 → ZIP → 재추출 대조
```

`build_steam_pack.py`는 팩을 쓴 뒤 원본과 팩만으로 완성본을 다시 만들어 해시를 대조하고, 어긋나면 실패로 끝납니다.
